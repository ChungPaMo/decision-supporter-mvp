### 성능 (모두 합성 자료, 실제 기업 파일은 재지 않음)

표의 칸은 `맞음 / 확인 필요 / 놓침 / 틀림`이다.

| 자료 | 사전만 | 사전 + 뜻 판단 |
|---|---|---|
| 처음 보는 양식 109개 | 82 / 3 / 19 / 5 | 103 / 5 / 1 / 0 |
| 이미 본 양식 200개 | 200 / 0 / 0 / 0 | 200 / 0 / 0 / 0 |
| 이희원 담당 합성 CSV 22개 | 16 / 1 / 5 / 0 | 18 / 2 / 2 / 0 |

"처음 보는 양식"의 103개(94.5%)는 틀린 파일을 본 뒤에 기준을 고친 수치다. 고치기 전에는 97개(89.0%)였다.

### 표 위치 찾기 (합성 자료)

| 자료 | 글자가 있는 첫 줄을 머리글로 | 표 위치 찾기 |
|---|---|---|
| 저장소의 더미 200개 (표 422개) | 42개 파일 | 200개 파일 |
| 다른 seed로 새로 만든 600개 (표 1,269개) | 131개 파일 | 600개 파일 |

규칙을 저장소의 200개를 보면서 만들었다. 새로 만든 600개는 양식의 종류가 같고 배치와 내용만 다르다.

### 올리지 않은 것 (이훤 PC에만 있음)

데이터 업로드 화면에 엑셀 여러 개를 끌어다 놓고 문서 종류를 분류하는 기능이다. 다른 담당 폴더를 고쳐야 해서 올리지 않았다.

- `modules/file_classifier/src/file_classifier/doctype_io.py`, `tests/test_doctype_io.py`
- `backend/app/api/document_sort.py`, `backend/app/main.py` (`POST /classifications/documents`)
- `frontend/src/components/DocumentSortPanel.tsx`, `DataUploadScreen.tsx`, `services/api.ts`, `styles/app.css`
- `contracts/openapi.json`, `docs/frontend_guide.md`

README의 "화면에서 쓰기"와 "코드에서 부르기"는 이 기능을 설명하므로, 올리기 전까지는 저장소와 어긋난다.

### 남은 일

1. **실제 기업 엑셀로 검증.** 지금 수치는 모두 합성 자료다.
2. **화면 일괄 분류 기능을 올릴지 결정.** 김대영(백엔드·계약), 정마나미(화면)와 협의가 필요하다.
3. **화면에 뜻 판단을 붙일지 결정.** CPU에서 파일 하나에 0.7초쯤 걸린다(200개면 2분 남짓). 메모리는 제대로 재지 못했다. ONNX 변환, 양자화, 낱말 벡터 저장은 해 보지 않았다.
4. **표 위치 찾기를 화면에 연결할지 결정.** 함수는 만들었고 백엔드의 표 범위 선택이 200개 범위를 모두 받아들인다. `/ingest/xlsx-layout`에 추천 범위를 넣을지는 김대영에게 제안해 뒀다([CONTRACT_REQUESTS.md](CONTRACT_REQUESTS.md) 0-1번).
5. **표 위치 찾기를 새로운 종류의 양식으로 검증.** 지금은 규칙을 만든 자료와 같은 종류의 양식으로만 쟀다.
6. **평면 BOM을 업로드 분류가 못 알아본다.** 표 범위를 넣어도 `Upper-part-id, Lower-part-id, Quantity` 양식 9개가 보류(`UNKNOWN`)로 나온다.
7. **시트별 분류.** 지금은 파일 하나에 답 하나다.
8. 발표 덱 두 개와 발표 대본은 옛 수치(91%)다. 저장소 밖 자료라 고치지 않았다.

## 날짜별 기록

### 2026-11-23

**표 위치 찾기** · `tables-0.1.0`
- 제목, 결재란, "항목: 값" 줄, 묶음 머리글, 합계 행, 한 시트의 여러 표가 있는 엑셀에서 표의 머리글 행·데이터 행·열 범위를 찾는다. 모델을 쓰지 않는다.
- 결과: 저장소의 더미 200개에서 표 422개를 모두 찾았다. 글자가 있는 첫 줄을 머리글로 보는 방식은 42개 파일이었다. 다른 seed 3개로 새로 만든 600개(표 1,269개)도 모두 찾았다.
- 과정: 첫 규칙으로 178개 → 머리글에 숫자(기간 번호)가 섞인 표와 듬성듬성한 첫 데이터 행을 받아들여 186개 → 표 위의 "항목: 값" 두 줄을 걸러 200개. 새 seed에서 나온 1건(머리글과 폭이 같은 작성일자 줄)을 보고 규칙 하나를 더했다.
- 백엔드 확인: 찾은 첫 표의 범위를 `/classifications/file`의 `table_selection`에 넣어 200개 모두 받아들여졌다. 범위를 넣은 뒤에도 192개는 보류(`UNKNOWN`), 3개는 재고 추천, 5개는 다른 등록 경로 안내다.
- 주의: 규칙을 이 200개를 보면서 만들었다. 새 seed 자료는 양식의 종류가 같다.
- 도구: `tools/eval_tables.py`, `tools/eval_tables_api.py`. 시험 12개.

**값 낱말을 모델에 넣지 않기** · `doctype-embed-0.3.1`
- 품목 코드, 전화번호, 날짜처럼 값으로 보이는 글자를 뜻 판단에서 뺐다. 세 자료 모두 결과가 같았고(103/5/1/0, 200/0/0/0, 18/2/2/0), 모델에 넣는 낱말이 파일당 48개에서 24개로 줄었다.

**CPU 속도와 작은 모델 비교** · 도구 `tools/eval_speed.py`
- BGE-M3 파일당 중앙값: GPU 38ms, CPU 1,205ms, 값 낱말을 뺀 뒤 CPU 683ms.
- 작은 모델(multilingual-e5-small)은 CPU에서 81ms로 빠르지만, 기준을 가장 유리하게 골라도 처음 보는 양식 109개에서 90개 맞음·5개 틀림이라 쓰지 않기로 했다.
- 메모리는 한 프로세스에서 모델을 차례로 올려 값이 섞였으므로 기록하지 않는다.
- 측정 환경: Python 3.11.9, torch 2.6.0, CPU 스레드 8개, RTX 4060 Laptop. 앞서 다른 계산과 겹쳐 돌린 측정은 버리고 단독으로 다시 쟀다.

**백엔드의 임시 변환 삭제**
- `backend/app/integrations/modules.py`의 `legacy_hold_kind`와 호출부를 지웠다. 모듈이 `hold_kind`를 직접 주므로 안내 문장을 읽어 변환하던 코드가 필요 없다.
- 김대영 담당 폴더지만 이훤의 지시로 직접 고쳤다. 지운 것은 21줄이고 다른 동작은 바꾸지 않았다.
- 검증: 전체 비DB 1149 passed / 66 skipped.

**처음 보는 양식의 오분류를 없애는 기준 두 가지** · `doctype-embed-0.3.0` · 커밋 `163ada4`
- 못 맞힌 12개를 하나씩 들여다봤다. BOM 구조표 6개는 뜻 판단 점수가 1.41점으로 필요한 1.5점에 못 미쳤고, MES 3개는 사전이 `Work center` 한 낱말로 CRP라고 답한 것이 그대로 나갔다.
- 필요한 점수를 1.5에서 1.3으로 낮췄다(기준 유사도 0.65의 두 배). 1.0~1.4에서 결과가 같았다.
- 사전 혼자 답했는데 확신이 "높음"이 아니고 뜻 판단에서 다른 종류 점수가 더 높으면 확인 필요로 돌린다.
- 결과: 처음 보는 양식 97 → 103개, 틀림 3 → 0건. 이미 본 양식 200개는 그대로. 이희원 자료 17 → 18개.
- 쓰지 않은 방법: 유사도 기준을 0.62로 낮추기(101개에 그치고 확인 요청이 늘었다).
- 주의: 틀린 파일을 본 뒤에 고쳤으므로 109개는 더 이상 "한 번도 보지 않은" 시험이 아니다.
