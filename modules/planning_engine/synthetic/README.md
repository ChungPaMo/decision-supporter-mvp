# ㈜충파모제지 합성 데이터 (SYNTHETIC)

계획 엔진 개발·검증과 E2E 시연에 쓰는 **가상 화장지 회사의 합성 데이터**다. 실제 기업에서 받은 데이터가 아니며, 공모전 수요기업(두루마리 화장지 제조사)의 업종만 참고했다. 회사·제품·수치는 모두 가정이다.

다시 만들기 (저장소 루트, 표준 라이브러리만 사용):

```powershell
python -X utf8 modules/planning_engine/synthetic/generate.py
```

`data/` 폴더를 매번 새로 만든다. 같은 `SEED`면 항상 같은 파일이 나온다. 숫자를 바꾸려면 `generate.py`·`masters.py` 위쪽의 설정 상수를 고친다. 생성 결과 요약은 [data/SUMMARY.md](data/SUMMARY.md).

| 코드 | 역할 |
|---|---|
| generate.py | 전체 생성. 월 판매량·재고·설비 시간 설계, raw 파일 작성, 변환 결과 대조 |
| masters.py | 기준정보(마스터) 테이블 정의 |
| sales_orders.py | 월 판매량 → 주문 건별 판매 현황 보고서 |
| operations.py | 2026년 생산실적·자재투입·구매발주·입고·재고수불부 (12/31 재고에서 거꾸로) |
| convert.py | raw → upload·derived 변환. raw 파일만 읽는다 |
| aggregate_sales.py | 판매 현황 → 월 수요 집계 규칙 (convert.py가 사용) |
| ledger.py | raw 거래 기록만 읽어 재고가 맞물리는지 확인, 월별 설비 사용시간 집계 |
| bottleneck_check.py | 예측 P50/P80/P90별 설비 부하·자재 여유·수량 한도 어림 점검 (`data/forecast/bottleneck_check.md`). 계획 엔진 정답 아님 |
| forecast_request.py | upload/05_monthly_demand.csv → 예측 엔진 입력 JSON (`data/forecast/request.json`, 기준일 2026-12-31, 3개월) |

## 1. 가상 회사

- **㈜충파모제지**: 두루마리 화장지 가공 회사. 점보롤 원단을 사서 **되감기·엠보 → 절단 → 포장**한다.
- 판매 이력 2022-01 ~ 2026-12 (60개월). 예측 기준일 `trained_until = 2026-12-31`, 계획 대상 2027-01 ~ 03.
- 단위: 제품은 팩(EA), 원단은 kg, 지관·필름·박스는 개(EA). 금액은 KRW.

`SUMMARY.md`의 "어림" 값은 설계 확인용(최근 12개월 평균 기준)이며 엔진 정답이 아니다. 정답은 별도 손계산으로 만든다.

**예측 엔진으로 확인한 결과** (2026-11-15, `forecast_request.py` → `python -m engine.forecast` → `bottleneck_check.py`)

- 예측: 9제품 모두 OK, 경고 0. 3개월 합계 P80은 P50보다 약 9% 높다. 백테스트(2026년)에서 P50 WAPE 약 8%, P80 적중률 약 71%(목표 80%보다 낮음, 성장 제품 때문에 예측이 약 3% 낮음).
- 1월은 설계대로: SAW1 P50 90% / P80 100% / P90 105%. MR-N3는 1/20 입고분이 없으면 P80부터 부족.
- 2월은 설 연휴로 시간이 줄어 P50에서도 SAW1·LB1이 정규+잔업 한도를 넘는다. 3개월 합계로 보면 SAW1이 P50 98%(1월 선행생산 + 잔업으로 겨우 가능), P80 106%·P90 112%(불가능). **희원 결정: 이 빠듯함을 그대로 둔다.** 계획 엔진은 못 맞추는 수량(부족분)을 반드시 보여줘야 한다.
- 선물세트: 모델이 2026년 성수기(2월)를 보고 2027년도 2월에 높게 예측한다. 2027년 설(2/7) 기준 실제 성수기는 1월이므로 명절 이동은 담당자 보정 대상. 이번 예측으로는 월 2,500 한도를 넘지 않는다.

## 2. 폴더 구조

**규칙: raw는 회사가 가진 것, upload와 derived는 우리가 raw에서 만든 것.**

```
data/
  raw/                     회사가 가진 원본 (회사 양식, 한글 파일명)
    master/                기준정보
    plans/                 생산팀 계획표
    transactions/          거래 기록 (판매 현황 2022~2026, 생산·구매·입고·수불 2026)
    snapshots/             기준일 현황 (재고, 미입고 발주)
  upload/                  시스템 업로드용. 전부 raw에서 변환 (convert.py)
  derived/                 분석용 집계. 전부 raw에서 변환 (convert.py)
  errors/                  검증 테스트용 오류 파일
  SUMMARY.md               생성 결과 요약
```

```
공급사 ──< 구매단가표 >── 자재 ──< BOM >── 제품 ──< 판매단가표
                                         │
거래처 ─────────────────────────── 판매현황(보고서)
설비 ──< 공정표 >── 제품      설비 ──< 월별가용시간계획

공급사 ──< 구매발주 ──< 입고 >── 자재 ──< 자재투입 >── 생산실적 >── 제품 ── 판매현황(출고)
                                  └──────── 재고수불부(월별) ────────┘
```

### raw/transactions/ — 판매현황_2022.csv ~ 2026.csv

| 기업·업소 | 약 7% | 호텔·병원·학교·빌딩관리 등 10곳 | 월 0~3회 불규칙 |

온라인 전용 제품은 온라인에서만, 업소용 점보롤은 기업·업소와 대리점에서만, 선물세트는 대형마트·온라인·기업 특판에서만 판다. 공휴일은 고정 공휴일과 설·추석 연휴, 일부 대체공휴일만 반영한 근사다.

**만드는 방식**: 생성기의 제품별 월 판매량을 채널 → 주문 날짜·거래처 → 주문 행으로 정수 그대로 나누고, 거래처명·제품명·단가는 마스터에서 찾아 붙인다. 취소·반품 행은 그 위에 따로 얹는다.

### raw/transactions/ — 2026년 생산·구매·재고 기록

판매현황(출고)과 12/31 재고현황은 그대로 두고, 그 사이를 채우는 기록이다. 품목마다 아래 식이 정확히 맞는다.

```
1월 기초재고 + 생산입고 + 구매입고 + 반품입고 − 판매출고 − 생산투입 − 반품폐기 = 2026-12-31 재고현황
```

| 파일 | 한 줄의 뜻 | 주요 컬럼 |
|---|---|---|

| 재고수불부_2026.csv | 품목·월 1줄 (ERP 월 수불 보고서) | 월, 품목, 기초재고, 생산입고, 구매입고, 반품입고, 판매출고, 생산투입, 반품폐기, 기말재고 |

- **기간**: 2026년 1년. 1월 입고분의 발주(2025년 12월 발주 8건)도 구매발주내역에 들어 있다. 12/28 발주한 `PO-2701-001`은 미입고로 남아 미입고발주현황과 같다.
- **생산**: 영업일에만. 재고가 하루 출고량의 1~2일치로 떨어지면 2.5~8일치를 만든다. 남은 설비 시간이 짧으면 작은 로트로 이어서 만든다. 불량률 약 0.8%(불량은 라인에서 폐기, 자재는 소모). 실제 작업시간은 표준시간의 96~104%.
- **설비 시간**: 2027-01 계획의 하루 정규시간(정규가용시간 ÷ 영업일)과 월 잔업 한도를 2026년에도 같게 본다. 절단기 SAW1은 월 가용시간의 약 89~98%를 쓴다(명절·성수기 전에는 미리 생산). 선물세트는 월 2,500세트 한도를 지킨다.
- **구매**: 자재별로 하루 평균 사용량의 10~12일치(최소주문량 이상)를 주문. 납기는 공급사 납품기간. 약 23% 지연(1~3일), 약 9% 조기 입고, 원단 발주의 일부(10건)는 두 번에 나눠 입고.
- **반품**: 반품입고 후 검수에서 전량 폐기(같은 날). 판매 가능한 재고는 늘지 않는다.
- **만드는 방식**: 12/31 재고에서 하루씩 거꾸로 올라가며 "그날 출고·투입된 만큼은 그 전에 있어야 한다"를 쌓고, 쌓인 양이 충분하면 그날 생산·입고한 것으로 기록한다. 그래서 기말재고가 재고현황과 정확히 같고 어느 날도 재고가 음수가 되지 않는다.
- **단순화**: 2026년 12월 주문 중 2027년 1월에 출고되는 45행(1,099팩)이 있지만 재고현황의 할당재고는 0이다.

## 3. 자동 검증

생성기가 매번 검사하며, 하나라도 어긋나면 멈춘다.

- **raw → 변환 대조**: 업로드·집계 파일의 기대값을 생성기 내부 값으로 따로 계산해 두고, `convert.py`가 raw에서 변환한 결과와 한 글자라도 다르면 멈춘다
- **월 수요**: 판매현황을 월로 합친 값이 원래 월 판매량과 같다
- **마스터 일치**: 판매현황의 거래처·제품 코드가 마스터에 있고, 거래처명·채널·제품명이 같다. 단가가 그 날짜의 판매단가표 값과 같고 금액 = 수량 × 단가
- **기간**: 거래처의 거래 기간 밖, 제품 출시일 전의 기록이 없다
- **BOM**: 원단 소요량 = 제품 규격(롤 길이 × 폭 0.1m × 겹수 × 롤 수) × 원단 평량
- **재고 맞물림** (`ledger.py`, raw만 읽음): 날짜별 재고가 음수인 날이 없고 12/31 값이 재고현황과 같다. 재고수불부 숫자가 거래 합계와 같다. 자재투입 = BOM 계산. 발주별 입고 합계·미입고수량·단가(구매단가표)·금액이 맞고, 미입고 발주가 미입고발주현황과 같다. 생산·입고는 평일에만
- **설비 시간**: 2026년 월별 사용시간이 월 가용시간(정규 + 잔업 한도)을 넘지 않는다

## 4. 확인한 것과 남은 것

- CAPA·라우팅 4개 파일은 `contracts.interfaces.capacity.CapacityRegistrationDraft` 검증과 승인 제품 참조 검사를 통과했다.
- 실제 업로드 API(DB)로 올려 보는 확인은 아직 하지 않았다.
- 셋업 시간·대체 설비·달력은 넣지 않았다. 현재 등록 규칙이 이 정책들을 받지 않는다.
- 재고 맞물림 검사가 실제로 잡는지 raw를 일부러 고쳐 확인했다(생산수량·입고 삭제·발주 단가·자재투입·수불부·재고현황·미입고 처리 7가지 모두 잡음).
- 생산·구매 기록은 2026년만 있다. BOM 버전 변경 이력은 없다.
