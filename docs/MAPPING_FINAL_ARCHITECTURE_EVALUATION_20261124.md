## 평가 범위

- Final은 고정 합성 130문서·1,132열이며 직접 매핑 정답 779열, HOLD 정답 353열이다. Confirmatory는 별도 생성한 100문서·980열이며 직접 매핑 정답 645열, HOLD 정답 335열이다. Confirmatory는 Phase 2의 로컬 결과가 이미 알려진 독립 입력이다.
- 세 텍스트 분리의 SHA를 검사했다. Solar와 Embedding의 입력은 제목, 헤더, 최대 세 개의 값 샘플, 통계 프로파일 및 표준 스키마·업무 설명이다. 문서 모델은 제조 파일 분류기 저장소에서 이미 관리하던 합성 XLSX와 그 파생 PDF를 사용했다. 실제 기업 자료, 레이블, 정답 및 생성 역할은 외부 입력에 포함하지 않았다.
- Calibration에서 제안 스키마별 2개씩 10문서를 사전에 선택했다. 문서별 응답과 필수 열 누락, 중복, 허용 필드를 비교해 정밀도 95%를 우선하고 `정답 − 2×오추천`으로 형식을 고정했다. 전체 문서에서 한 열만 실패했을 때의 효과는 동일 응답으로 기존 엄격 정책과 안전한 부분 채택을 모두 채점했다.
- Phase 2 캐시를 재사용했다. 모델·요청 본문 SHA가 같은 조합은 한 응답을 공유하고, 실패한 동일 요청의 자동 재전송을 차단했다. 각 외부 요청은 모델별 속도를 제한하고 공유 원장에서 보수적 비용을 예약했다. Phase 3의 USD 10은 Phase 2 원장 USD 1.12965941을 포함한 한도다.

## 결과 읽는 법

정확은 Top-1 추천 수, 오추천은 정답이 다른 필드이거나 HOLD 정답에 붙인 추천 수다. 오추천율 분모는 전체 열, 정밀도 분모는 추천이 있는 열이다. 전체 일치 문서에는 정답 열과 HOLD가 모두 맞아야 한다. Solar는 한 열에 단일 후보 또는 HOLD를 반환하므로 별도 Top-3 순위를 제공하지 않는다. `계약 영향`은 적어도 한 요청이 응답 조건을 위반한 문서이며, 부분 검증을 적용하면 같은 문서의 검증된 다른 열은 가용하다. 지연은 공급사 요청 P50이고 캐시 적중 읽기 시간은 제외한다.

### Embedding 보충 비교

Embedding 2는 승인된 전체 입력에서 Top-3를 계산했고, Mini 확인 요청은 각 분리의 10문서에 한정했다. Final 91열에서 정답 21·오추천 3·HOLD 67, Confirmatory 100열에서 정답 23·오추천 7·HOLD 70이었다. 계약 영향은 각 2문서와 4문서였다. 작은 표본에서 유리한 근거가 없어 기본 후보 생성에 Embedding을 추가하지 않는다. 컬럼 단독 및 분할 방식도 보정 결과를 근거로 전체에 반복 호출하지 않았다.

## Excel 위치 역추적과 필드 추출 방법

Document Parse가 출력한 머리행 전체와 열 순서를 원본의 모든 표시 시트에서 검색했다. 유일한 헤더만 잠정 연결하고 원본의 연속 행을 확인했다. 반환된 행 수와 다르거나 숫자가 있는 본문 행이 헤더로 제안되면 HOLD한다. 원본 데이터를 다시 읽어 SHA·시트·행번호·열 및 셀 주소를 반환한다. 수식은 원본 캐시 값의 가용성에 따르며 API의 렌더링 좌표를 Excel 셀 주소로 직접 해석하지 않는다. 제목과 형식, 동일 머리가 반복되는 복수 표·시트는 사용자 `xlsx-layout` 선택을 유지한다.

평면 BOM은 제품·자재 코드 쌍이 원본에 유일하게 존재하는 경우만 행과 연결한다. 같은 문자열, 숫자 등가·표기 변경, 누락 필드, 원본에서 근거를 확인하지 못한 값, 연결되지 않은 행을 분리했다. 복합 BOM에는 정규화 행 정답이 없어 구조와 추출 형식만 기록했다. 필수 항목이 실제로 비어 있거나 원본 자료형이 다른 경우를 충분히 검증한 별개의 입력셋은 필요하다. [Extract 입력 형식과 페이지 상한](https://console.upstage.ai/ko/docs/models/information-extract) · [Extract 스키마](https://console.upstage.ai/docs/capabilities/extract/writing-a-schema) · [Parse API](https://console.upstage.ai/api/parse/document-parsing)

| Enhanced | 1 | 0 | 19 | 9 | 2 | 2 |

HOLD 수는 공급사 후보 기준이라 정답 24개와 분모가 다르다. Auto는 모든 페이지에 Standard를 선택했다. Standard·Auto는 평면 BOM 두 문서와 ERP 재고의 셀 범위를 찾아 원본 데이터를 다시 읽었다. Enhanced는 평면 BOM에서 데이터 행을 두 번째 표의 헤더로 제안한 사례가 있어 숫자가 있는 헤더를 HOLD에 포함했다. 허용된 범위만 비교하면 잘못 연결된 범위는 0건이지만 정확한 전체 범위가 3/24라 자동 탐지 범위가 제한적이다. 복수 표와 헤더 반복은 기존 사용자 선택을 유지해야 한다.

같은 위치의 Parse 셀 문자열 일치는 Standard·Auto 664/1,933, Enhanced 545/1,933이었다. 헤더로 대응된 공급사 표는 Standard·Auto 17개, Enhanced 22개였다. 숫자가 실제로 같은 셀은 대응 표의 숫자 셀 중 Standard·Auto 264/800, Enhanced 224/930이었다. 표 후보 수와 안전하게 연결한 범위 수, 이후 원본 값 보존은 별개다.

같은 두 평면 BOM에서 Standard의 위치 검증을 거쳐 원본을 다시 읽었을 때 72행과 80행을 보존했고 Solar는 **2/6열 정답·4오추천**이었다. 파생 PDF를 Enhanced로 파싱해 Solar에 주면 **4/6열 정답·2오추천**이었지만 입력 표는 일부만 남아 29행과 34행이었다. 두 파이프라인 모두 세 열이 모두 맞은 문서는 0/2였다. 원본 값을 보존해도 매핑의 의미 검토가 필요하고, 열 추천 수만으로 원본 데이터 보존율을 비교할 수 없다.

동일 평면 BOM PDF에 대한 Extract의 Standard·Enhanced 총 4회는 429 또는 60초 응답 시간 초과였다. 복합 BOM PDF의 Enhanced도 시간 초과로 정답 값 채점은 불가능했다. 별도의 미등록 문서 PDF에서 Enhanced는 BOM 스키마에 맞춘 **23행과 비어 있지 않은 값 92개**를 반환했다. 실제 BOM 등록 대상이 아닌 입력이므로 추출된 행을 시스템 후보로 사용하면 안 된다. 이 조건의 값 정답률을 추정하지 않았다.

**Information Extract Enhanced 원본 XLSX**는 72행짜리 같은 평면 BOM을 직접 1회 요청했다. 60초 안에 응답이 없었고 페이지·값·셀 위치를 확인하지 못했다. 동기 공식 상한 100페이지의 **USD 6.60 예약을 유지**했다. Standard 원본 XLSX는 100페이지 상한 예약을 감당할 수 없어 미실행이다. 원본과 동일 내용 PDF의 행 개수·정확 행·정확 값·추가 값·숫자·날짜·코드 비교는 응답 실패로 미검증이다. 이전 6행씩의 5문서 결과(Enhanced 209/210값·완전 일치 29/30행)는 별도 소규모 실측으로 유지한다.

Document Classify의 원본 XLSX 두 건은 BOM과 MRP를 각각 맞췄고, 응답 지연은 12.29초와 16.35초였다. 나머지 4건은 원장 상한 때문에 미실행이다. 성공 응답에 페이지 계량값이 없어 두 건의 최대 예약 USD 0.88을 유지했다. OCR은 파생 PDF 3건·실제 4페이지에서 표 헤더 문자열 21/21을 찾았고 P50 약 10.70초였다. OCR은 표의 셀·행 구조를 직접 반환하지 않으므로 매핑·범위 역추적 성공으로 세지 않았다. [OCR 공식 계약](https://console.upstage.ai/api/parse/document-ocr)

**선정안은 A를 기본으로 하고, C와 E는 불확실한 사례의 보조 검토 단계에 제한하는 구조**다. 정상 Excel은 `xlsx-layout`와 사용자 범위를 거쳐 원본 셀을 읽는다. 이미 확인된 필드를 보전하고, 미확정 열만 외부 사용 승인이 있을 때 검토한다. 표준 필드·형식·중복·원본 근거와 사용자 확인을 모두 유지한다. 업무 지식은 버전이 붙은 표준 스키마의 일부로 관리하고, 추출과 승인 계약은 별개로 둔다.

LightGBM과 Embedding은 양쪽 표에서 정밀도나 검토량의 일관된 개선이 없어 기본 구조에서 제외한다. Preview는 가장 빠른 원격 후보였으나 고정 두 분리에서 정밀도 95%를 넘지 못했고 지원 종료 일정도 있다. 고객별 독립 문서에서 유형·헤더·열·값·필수 항목을 따로 라벨링하고, 코드·날짜·단위 및 반복 행과 잘못된 문서 유입을 반드시 시험한다. 외부 서비스 장애, 페이지·비용 계량 실패, 파일 근거가 사라진 경우에는 원본 파서와 수동 매핑을 유지한다. 실제 기업 자료의 외부 전송이나 운영 적용을 연구 승인으로 간주하지 않는다.

`calibrate`와 `evaluate --split final|confirmatory`는 외부 실행 승인 및 `--approved-paid-api`가 필요하다. Document Intelligence는 `run --parts layout classify-ocr extract-pdf solar extract-xlsx`를 사용한다. 이미 고정한 문서 SHA와 기존 캐시·원장을 보존해야 한다. 원본 XLSX의 페이지 상한은 공식 동기 엔드포인트 기준으로 예약하며 응답에 페이지 계량값이 없으면 보수 예약을 유지한다. 계정 청구서를 조회하는 재현 절차는 포함하지 않았다.

운영 코드·팀원 모듈·DB 변경은 없다. 전체 비DB pytest **1,264 통과 · 68 건너뜀**, 관련 연구 25건 통과, OpenAPI·JSON Schema 동기화 통과다. 변경 범위의 보안 탐지와 로컬 키 문자열 일치는 각각 0건이었다.
